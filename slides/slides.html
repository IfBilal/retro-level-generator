text2mario

Type a sentence, play a verified Mario level

A text-conditioned diffusion model, a playability checker, a browser game and a Streamlit app.

AI2002 Software Category, Path A. All numbers on these slides are generated from saved result files.

1/12

1. The problem and who it is for

  • A platformer level is a tile grid; a first draft by hand is slow.
  • Random generators are hard to steer; learned ones ignore words and rarely check that the level can be finished.
  • Users: indie/hobby level designers (steerable drafts, export), students of procedural generation (inspectable pipeline), demo users (play it).
  • Input: one sentence + width + guidance + seed. Output: framed 16-row level, canonical caption, badge, PNG, playable HTML, JSON/CSV/VGLC.
  • No user study was run: the needs are stated, not measured.
2/12

2. Objectives and scope

  • O-1 content follows the prompt (C-score)   O-2 valid structures (no broken pipes/cannons)
  • O-3 verify beatability and measure how far to trust it   O-4 do not copy training windows
  • O-5 honest evaluation on unseen levels (level-grouped split, one-shot test)   O-6 deployed Streamlit app
  • Scope: one game family (SMB1/SMB2 tiles), 16 rows, widths 16-112, five quantity buckets, no positions.
3/12

3. Data and leakage prevention

  • MarioDiffusion corpus: 7,687 windows (16x16, 13 tile classes) from 42 levels; captions in a fixed grammar.
  • Split by level: 31 train / 5 dev / 6 test (windows overlap by 15 of 16 columns); near-duplicate families kept together; hash-locked.
  • Our caption detector reproduces 7,687 / 7,687 stored captions (written from the grammar, not ported).
  • Tuning on dev only; test used once (guards in code and tests).
4/12

4. The technique: diffusion + text + guidance

  • x_t = √ẽt x0 + √(1-ẽt) ε; a U-Net predicts ε (MSE); DDIM-50 sampling with x0 clipping.
  • Frozen MiniLM tokens → trainable adapter (66,048 params) → cross-attention in the U-Net (18.3 M params).
  • 10 % caption dropout → classifier-free guidance εu + w(εc - εu).
  • Long levels: stride-8 windows with RePaint known-region replacement; framed start and flag.
5/12

5. System pipeline

  • Normalizer: 30/30 on the dev prompts, 100 % passthrough of all stored captions.
  • Failed check → re-sample the stuck window (max 5 per window, 20 per level). Same prompt + seed → same level.
6/12

6. Playability checker and game

  • A* with jump arcs simulated by the game's own integrator; physics in one shared file; conservative margins; enemies killable.
  • Real train/dev levels solved: 0.694 (full), 0.799 (windows) — target 0.90 not reached.
  • Reference-solver agreement 0.663 (≥ 0.85 needed): gate failed, so selection uses Snoplay.
  • Evidence instead: game-engine contract test (0 unsound of 8), ghost-bot replay 0.750 of 40 real windows.
7/12

7. The Streamlit app

  • Prompt box + examples → what the model will understand (scenes, clamps, ignored words) → generate → badge + embedded offline game + downloads.
  • Input validation with readable errors; CPU fast mode (25 steps) automatic without a GPU; cloud profile with a time budget.
  • Measured (median): 4.820 s for 48 columns and 12.900 s for 112 columns in fast mode on the RTX 3060 Ti; full quality takes 35.540 s / 167.330 s; CPU fast mode 3.850 s / 25.910 s. The 10 s target is not met at 112 columns.

10. What did not work (and what we did about it)

  • G-P3 failed: broken structures fall with training while copying rises; aux-CE trades one for the other. We chose cosine, documented a waiver, and judged the conditional model on its own metrics.
  • G-P5b failed: the reference solver is not a usable oracle here; fallback Snoplay.
  • Four bugs found by tests/e2e runs and fixed with regression tests.
11/12

11. Limitations and conclusion

  • 31 training levels; coarse captions (no positions, 5 buckets); one game family; 5 dev / 6 test levels → wide intervals; no human playability study.
  • "Verified" = a conservative physics claim by our checker, not a proof for every player.
  • Cloud deployment needs the team's Streamlit/GitHub login; the repo is prepared (DEPLOY.md).
  • Conclusion: a complete, honestly evaluated text-to-level system; failures are reported with evidence and fallbacks.
